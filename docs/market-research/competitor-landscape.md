# Synoikia faces many partial rivals, none complete

No product we found ships Synoikia's full combination in one free, self-hosted package. That combination is per-service plugins, access levels per operation taken from the upstream API, an approval page that the calling client cannot answer, Code Mode in a sandbox, secret redaction, a unified audit log and signed plugin repositories. Each part does exist somewhere else. Cloudflare and Bifrost ship Code Mode with a sandbox. Peta, TrueFoundry, Barndoor, Permit and hoop.dev ship approvals that a human gives outside the client. Kong, agentgateway, Pomerium and Obot ship RBAC per tool. Lasso ships secret masking. In the homelab, ha-mcp has copied much of the playbook for Home Assistant. The market is large, crowded and moving toward enterprise buyers. Gartner, as quoted by vendors, calls MCP support a mandatory gateway feature and expects 75% of API gateway vendors to have it by the end of 2026. Funded vendors sell SSO, SASE and compliance to enterprises, and many of them have been bought. Synoikia's gap in the market is real but narrow: security-first control of self-hosted services on a private LAN, with no cloud dependency. Its main weaknesses are ecosystem size (it cannot proxy existing MCP servers), a single-node design, no egress control for plugins yet, and its early-development status. The largest threats are Docker's MCP Gateway, Home Assistant's own MCP work and ha-mcp, and Cloudflare portals, which can now reach homelabs through Tunnel.

**How to read this report.** The research ran on 2026-10-23. GitHub was blocked in the research session (HTTP 403), so **no GitHub star counts, commit dates or release cadences could be verified**. The one exception is a README fetch for ha-mcp. Most sources are search-engine extracts, and many are vendor-written "best MCP gateway" roundups (Maxim/Bifrost, Lunar, Composio, TrueFoundry, Zuplo, Speakeasy, MintMCP). Items marked **(unverified)** are single-source, from a competitor, conflicting, or from researcher prior knowledge. Synoikia's own features come from its README, which is authoritative here.

## Synoikia's baseline: seven controls in one box

Synoikia replaces several separately deployed MCP servers with one server that plugins extend. Each plugin instance gets its own endpoint with three tools: `search(code)`, `execute(code)` and `resume`. Model-written code runs in an `isolated-vm` sandbox with no Node APIs, network or timers. Every operation has an access level of **None, Read, Ask or Write**, set per group. **Whether an operation reads or writes comes from the upstream API**, not from tool annotations. Ask calls wait for a human on **Synoikia's own approval page**, which the calling client cannot answer. Clients that support URL-mode elicitation open the page, and chat clients show an approval card. Destructive operations are `locked` by default. They need a typed confirmation and can never be pre-approved or set to Write. Each client gets a ceiling, read-only by default, with OAuth 2.1, bearer tokens or Cloudflare Access. Plugins run in separate child processes under the Node permission model. Secrets are encrypted at rest and redacted from results, logs, approvals and audit. The admin portal has TOTP and OIDC. Plugins are verified with minisign. The license is MIT. The README states three limits. The project is in early development and "not yet recommended for production use". Core does not restrict plugin network egress yet (issues #108 and #111). Deployment is a single Docker Compose node.

That baseline sets the comparison axes in the matrix below. They are self-hosting, license and price, proxying of existing MCP servers, out-of-band human approval, access levels per operation, context reduction, redaction and audit.

## Open-source self-hosted gateways mostly proxy, rarely gate

Nearly every open-source gateway is a proxy or aggregator for existing MCP servers. They focus on authentication, routing and observability, and they pass full tool lists through. This is the biggest structural difference from Synoikia. Synoikia needs purpose-built plugins, so its ecosystem is small. In return it can classify each operation as a read or a write from the upstream API, which no proxy can do reliably. Proxies depend on MCP's `readOnlyHint` and `destructiveHint` annotations, and a malicious server can set those to any value. Only **Bifrost** (production Code Mode in a Starlark sandbox) and **Docker MCP Gateway** (experimental `code-mode`) overlap with Synoikia's sandbox design. No open-source gateway found combines Code Mode with an out-of-band approval page.

The audience splits three ways. **Enterprise and Kubernetes:** agentgateway, Envoy AI Gateway, Microsoft MCP Gateway, Archestra, ContextForge, Obot and Kong. **Developer desktop:** Docker and ToolHive. **Homelab-friendly aggregators:** MetaMCP, MCPJungle, 1MCP, Unla and mcp-gw. None of the homelab-friendly tools offers approvals, redaction or access levels per operation ([Maxim open-source list](https://www.getmaxim.ai/articles/open-source-mcp-gateways-for-developers-in-2026/), [Lunar comparison](https://www.lunar.dev/post/the-best-open-source-mcp-gateways-in-2026)).

## Managed platforms sell SaaS reach and enterprise identity, not LAN control

Commercial vendors fall into four groups. **Enterprise MCP control planes** sold to security and IT teams: Runlayer, Natoma, Mintive, Barndoor, TrueFoundry, Peta and Permit. **SaaS integration platforms** that hold managed OAuth tokens: Composio, Arcade, Zapier, Pipedream, Merge, Nango, Paragon and Unified. **Hyperscaler and API-gateway add-ons**: Cloudflare, AWS, Azure APIM, Apigee and Kong. **MCP auth vendors**: Descope, WorkOS and Auth0. Almost all of them target SaaS apps and enterprise IdPs. Prices are per user, per call, per credit or by quote. None is built for self-hosted homelab services. For a homelab user, every managed option sends credentials or traffic off the LAN. Even Cloudflare terminates TLS and sees the traffic. That is Synoikia's strongest argument against this segment.

**Cloudflare** is the closest technical rival. Its MCP server portals put many servers behind one URL, and **Code Mode on portals** replaces all upstream tools with search and execute. Model-written JS runs in an isolated Dynamic Worker, and the setting can be off, opt-in, default or enforced. A write-up of Cloudflare's post shows a four-server portal going from about 9,400 tokens to about 600 ([zenn.dev](https://zenn.dev/oymk/articles/45e38ede000716?locale=en), [Cloudflare blog](https://blog.cloudflare.com/enterprise-mcp/)). **Since 2026-09-22, portals can front MCP servers that exist only on a private network**, reached through Cloudflare Tunnel or Mesh ([changelog](https://developers.cloudflare.com/changelog/post/2026-09-22-private-mcp-servers/)). Many homelabbers already run Tunnel, and Synoikia's own README suggests it. The weaknesses for Cloudflare are approvals and lock-in. Approvals are an Agents SDK pattern you code yourself ([HITL docs](https://developers.cloudflare.com/agents/concepts/agentic-patterns/human-in-the-loop/)). An open issue says approval flows with Code Mode "are not yet coherent", because approving generated code is harder than approving one tool call ([issue #1148](https://github.com/cloudflare/agents/issues/1148)). Synoikia solves this by gating each operation _inside_ the code run. Cloudflare also requires a Cloudflare zone and a Zero Trust IdP, and **no separate portal price was found**.

## Approvals the client cannot fake remain the scarcest feature

Most human-in-the-loop features sit inside the agent host or the client. Examples are OpenAI Agents SDK `needsApproval` and `require_approval` ([OpenAI](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)), Cloudflare Agents HITL, LibreChat's global `toolApproval` and Goose's modes. Goose **runs autonomously by default** when `GOOSE_MODE` is unset ([Goose docs](https://goose-docs.ai/docs/guides/managing-tools/goose-permissions/)). LibreChat by default runs tools without asking ([LibreChat docs](https://www.librechat.ai/docs/features/mcp)). These approvals protect against model mistakes. They do not protect against an injected or compromised host, because the approver code runs in the same process as the agent. MCP elicitation in form mode is also in-band. Server-side approvals that a human gives elsewhere appear in only a few places: Peta, TrueFoundry, Barndoor, Permit (Enterprise), hoop.dev, n8n, and three small open-source gateways.

## Five trends: commoditized Code Mode, consolidation, spec churn

**Code Mode went from experiment to table stakes in about a year.** Cloudflare proposed it in September 2025. Anthropic published "Code execution with MCP" in November 2025, with an example that cut tokens from about 150,000 to 2,000 ([Anthropic](https://www.anthropic.com/engineering/code-execution-with-mcp)). Cloudflare's own API server covers the whole Cloudflare API with two tools in about 1,000 tokens ([Cloudflare](https://blog.cloudflare.com/code-mode-mcp/)). Docker, Bifrost and utcp-mcp-gateway followed, and Cloudflare portals turn it on by default. The savings depend on scale. An independent AIMultiple test on one server measured **78.5% fewer input tokens but 7% higher latency** ([AIMultiple](https://aimultiple.com/code-execution-with-mcp)). Client-side deferred tool loading also shrinks the problem. Anthropic's Tool Search Tool claims about 85% savings ([mcp.directory](https://mcp.directory/blog/mcp-context-bloat-fix-2026-tool-search-code-mode-progressive-disclosure)), and ha-mcp says its 87 tools cost "near-zero idle cost" in Claude clients. Synoikia's three-tool shape is on trend but no longer unique. A homelab with 5 to 15 services gets smaller absolute savings than an enterprise with 500 tools. The token argument still matters most for local models and clients without deferred loading.

**Consolidation is fast, and the buyers want enterprise distribution.** Snyk bought Invariant, SentinelOne bought Prompt Security, CrowdStrike bought Pangea, Cato bought Aim, and Palo Alto bought Protect AI in 2025 ([guptadeepak M&A tracker](https://guptadeepak.com/agent-security/deals/)). In 2026 the MCP layer itself consolidated: Boomi bought Lunar, Arcade bought Smithery, Snowflake bought Natoma, Workday bought Pipedream, and Palo Alto bought Portkey (unverified). Gartner, as quoted by Kong, sizes the AI gateway market at **under $250M today and $1B by 2028** ([Kong](https://konghq.com/resources/reports/gartner-complimentary-report)). It also predicts that **by 2027 over 40% of enterprise MCP deployments will have security incidents** ([Tray.ai](https://tray.ai/blog/mcp-enterprise-security-risks/)). Both figures are second-hand. An MIT homelab project is not on this acquisition path and does not compete for this budget. Acquisitions that change roadmaps and licenses do give it a credible "you own it" argument.

**The 2026-07-28 spec changes the ground under every gateway.** The `initialize` handshake and `Mcp-Session-Id` are retired. Requests carry `Mcp-Method` and `Mcp-Name` headers so that gateways can route without parsing JSON. Tool lists become cacheable. Multi Round-Trip Requests replace held-open elicitation streams. Dynamic Client Registration is deprecated in favor of Client ID Metadata Documents ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)). URL-mode elicitation lost `elicitationId` and the completion notification. Clients now learn the outcome by retrying the request, with the server's own identifier in `requestState` ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). This maps well onto Synoikia's `resume(executionId)`. But Synoikia's README still describes `Mcp-Session-Id` passthrough and cites the 2025-11-25 elicitation spec, so a migration is due. MCP itself now sits in the Linux Foundation's Agentic AI Foundation, and the TypeScript and Python SDKs have each passed 1B downloads ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/)).

**The "CLI and Skills instead of MCP" backlash produced a layered consensus.** In early 2026 an "MCP is dead" HN thread appeared, and Perplexity's CTO said Perplexity was moving to APIs and CLIs ([Milvus](https://milvus.io/blog/is-mcp-dead-cli-and-skills-for-ai-agents.md)). The emerging view gives procedural knowledge to Skills, local developer tools to CLIs, and authenticated remote services with permissions to MCP ([DEV](https://dev.to/trashwbin/cli-vs-mcp-vs-skills-the-whole-debate-is-asking-the-wrong-question-nc1)). That third layer is where Synoikia lives. Synoikia can present itself as the safe alternative to giving an agent `curl` and your API keys.

**Security posture is now the main buying criterion** in vendor roundups ([Speakeasy](https://www.speakeasy.com/blog/best-mcp-gateways-for-enterprise-2026)). Yet nearly all of them define security as authentication, RBAC and guardrails, not as a human approving each call.

## Where Synoikia leads, lags, and could lose

**Differentiated.** Four of Synoikia's claims hold up against every tool in the evidence. First, **access levels derived from the upstream API** rather than from annotations or policy that admins write. Second, **locked destructive operations** that need a typed confirmation and can never be pre-approved. Third, **an approval page the calling client cannot answer, integrated with Code Mode**, so that a sandboxed script pauses at one operation and resumes later. Cloudflare's own issue tracker says it has not built this into a product. Fourth, one free MIT package that keeps secrets and traffic on the LAN. Redaction, audit, signed plugins, client ceilings and isolated plugin processes each exist elsewhere. In the self-hosted homelab segment, only Synoikia offers all of them together.

**Behind.** First, **coverage**. Synoikia cannot proxy existing MCP servers, while nearly every rival can. ContextForge, Unla, Kong and Apigee also turn REST or OpenAPI into MCP through configuration, which is a lower barrier than writing a plugin. Second, **isolation**. ToolHive (containers per server), Archestra (egress limits per environment) and Cloudflare (default-deny egress in Dynamic Workers) restrict network access, and Synoikia does not yet. Third, **maturity and scale**. Synoikia is a single node in early development. It has no Postgres or Kubernetes HA, no SSO or SCIM provisioning, no SIEM export integrations, no discovery of shadow MCP servers, and no compliance attestations. Fourth, **approval granularity**. WhereMyMCP binds each approval to one exact argument object. Peta and n8n send approvals into Slack, Teams and Telegram, where Synoikia offers ntfy and webhooks. Fifth, **community**. ha-mcp alone reports thousands of stars and support for 15+ clients, and the long tail covers services Synoikia has no plugin for.

**Threats, in order of likelihood.** First, **ha-mcp and Home Assistant**. ha-mcp already has read-only mode, a delete split, approval hooks and tool search, and it targets Synoikia's most obvious plugin. HA's reported move to expose more integrations natively (unverified) would raise the pressure. Second, **Docker**. It already ships a catalog, a local gateway and a code-mode sandbox on every developer desktop, and it lacks only approvals and policy. Third, **Cloudflare**. Portals with Code Mode now reach private networks through Tunnel, which many homelabbers already run. A free small Zero Trust tier would remove the price barrier, but portal pricing was not confirmed. Fourth, **clients absorbing the value**. Native tool search, deferred loading, and MRTR and URL elicitation in clients reduce the gateway's context-cost and UX advantage. Fifth, **spec churn**, which uses up a small team's capacity.

## Conclusion

The evidence moves Synoikia's moat away from where its README puts it first. Context cost was the original pitch, and it is now the weakest differentiator. Cloudflare, Docker and Bifrost commoditized Code Mode, and clients now handle tool bloat themselves. The defensible position is the security model _wrapped around_ the sandbox. That means server-enforced, API-derived access levels, locked operations, and approvals that a compromised client cannot forge, inside a box the user owns. The market's direction makes this more valuable. Funded vendors are being bought for enterprise distribution. Gartner expects widespread MCP security incidents. Homelab media is converging on "don't give agents direct access". Yet no funded player serves the private-LAN buyer.

The strategic choice follows from this. Synoikia's biggest weakness is reach: no proxying of existing MCP servers, and few plugins. A bridge that puts third-party MCP servers behind the same gate would answer the most common objection. It would bring proxied tools under ceilings, approvals, redaction and audit, even if they fall back to annotation-based classification. Two engineering items would close the gaps rivals already exploit and keep pace with clients: egress control for plugins (issues #108 and #111) and migration to the 2026-07-28 spec. Without these, Synoikia risks becoming the most principled option that few people can adopt. With them, it becomes the self-hosted answer that the enterprise-focused market has left open.
