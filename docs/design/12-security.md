# §12 Security

## Trust boundaries

| Boundary                    | Controls                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Internet → admin            | Separate port that the proxy does not publish (§11). Sign-in with TOTP or OIDC, sessions, CSRF, lockout (§6.1).                                                                                                                                                                                                                                                                                                                                                                                               |
| Internet → MCP endpoint     | Client auth methods enabled globally and narrowed for each endpoint, scoped tokens and grants, 403 outside the scope, access ceiling `read` by default (§6.2, §6.3). Each credential has an enabled owner whose role has the endpoint. The `external` method accepts only a user that the external provider identifies with a verified assertion.                                                                                                                                                             |
| User → admin                | Only the Admin role uses admin routes; all other routes are admin-only unless listed (§8.4). A role maximum and a personal level never open more than the endpoint level (§5.2.1). Own rules apply only to their owner (§6.4).                                                                                                                                                                                                                                                                                |
| MCP client → upstream       | The sandbox gives access only to the binding. The gate decides each call (§5.2). Then the plugin `invoke` runs.                                                                                                                                                                                                                                                                                                                                                                                               |
| Model → configuration       | No MCP tool changes configuration. The sandbox has no database access.                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Plugin → core secrets       | Child process, Node permission model, clean environment, secrets of its own instance only (§4.4).                                                                                                                                                                                                                                                                                                                                                                                                             |
| Plugin supply chain         | Pinned versions, sha256, optional pinned-key signatures, warnings for unsigned plugins, prebuilt packages only (§4.2, §4.3).                                                                                                                                                                                                                                                                                                                                                                                  |
| Approvals                   | Only the owner of the calling credential decides, on the approval page. Core identifies the owner by a page sign-in, or by the external provider of an endpoint that allows `external`. The answer of the calling client never approves, except opted-in in-session approvals (form prompt or approval card) of operations that are not locked. The approval card decides nothing else. Hash-bound, single use, typed confirmation, parameters in memory only, access and targets checked again (§5.3, §5.7). |
| Plugin change during a call | The gate refuses a call if the bundle changed after the call was gated (§5.2).                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Secrets at rest             | AES-256-GCM, master key outside the database, APIs that only write secrets, redaction everywhere (§5.5, §7.2).                                                                                                                                                                                                                                                                                                                                                                                                |
| Audit                       | Append-only. It records calls, searches, configuration, sign-ins and plugin events. The model never sees it.                                                                                                                                                                                                                                                                                                                                                                                                  |

## Remaining risks

1. An installed plugin that is malicious can give wrong classifications or locks for its own upstream. It can also connect to any network host. The trust flow (§4.3) and an egress policy (§11) reduce this risk. Core does not.
2. The `external` method accepts each user that the Cloudflare Access application lets in. The Access policy, not core, decides who that is. Core refuses service tokens.
3. SQLite allows one writer, so there is one core process.
4. Core decides if a call is a read or a write once, before the approval wait. A sync from the same bundle can change an operation that has its own `ask` from read to write while its approval is open. The approved call then runs without `prepareWrite` and without the write budget. A human approved these exact parameters, and the risk lasts for one approval only.
5. A session grant (§5.8) lets a client run each `ask` operation of one endpoint without a human, for up to `sessionGrantMaxHours`. During that time, a client under prompt injection can make these calls. Locked and typed-confirmation operations, the write rate limit, revoke and the audit log limit this risk.
6. Without the approval card, the agent shows the approval link as text. An agent under prompt injection can show another link. The real page needs the owner, identified as for URL elicitation, and a POST with a CSRF token.
7. A parked execution keeps an isolate and the real parameters in memory until its approval ends. The parked limits, the stop after an approval that is not given, and the limit of 10 approvals for each execution (§5.6) bound this.
8. The approval page asks for no TOTP code. A browser that stays signed in, for up to `approvalSessionAbsoluteDays`, can approve calls and give session grants without a new sign-in. A locked operation still needs its typed confirmation. A TOTP change and **Sign out all approval browsers** in the profile end these sessions.
9. Self-registration with the Admin role as default role makes each new user an admin. That includes each identity that the external provider identifies. The portal asks for a typed confirmation, and self-registration is off by default (§6.5).
10. On an endpoint that allows `external`, the approval page accepts the identity from the external provider (§5.3). A client that holds the provider identity of the user, for example a Cloudflare Access token, can open the approval link and approve its own call. There, approvals guard against mistakes of the agent, not against a hostile client.
11. In-session approval (§5.3) lets the calling client approve its own `ask` calls: a form answer or an `approval_decide` call comes from the client. A client under prompt injection can then approve these calls. A client that accepts prompts automatically also approves these calls. The setting is off by default and the portal warns about it. Locked and typed-confirmation operations still need the page. Core checks the setting again at each card decision, and the audit records the channel.
12. The MCP client policy (§6.6) matches a client name that the client declares itself. A client can send the name of another client and pass an allow list or a deny list. The policy is not a security boundary. Client auth, the access ceiling and the gate are the boundary.
